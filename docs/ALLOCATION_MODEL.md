## 0. 두 개의 질문을 분리한다

이 시스템의 가치 주장은 사실 두 개인데, 지금까지는 하나만 측정해 왔습니다.

| | 질문 | 지금 상태 |
|---|---|---|
| **Q1** | 주차 요원 없이도 운전자가 자리를 찾는가? | ✅ 답했음 |
| **Q2** | 주차장의 **흐름**이 실제로 좋아지는가? | ⚠️ **아직 제대로 묻지 않았음** |

Q1 은 `runs/compare-baseline/` 이 답합니다. 평균 주차소요 53.7초 → 28.4초(−47%),
우회거리 52.6m → 2.0m(−96%). 이건 **개별 운전자의 경험**입니다.

Q2 는 다릅니다. 혼잡은 개인이 아니라 **계(system)의 성질**입니다. 한 대의 소요시간이
줄었다고 통로가 덜 막힌다는 보장은 없습니다. 오히려 모두를 같은 좋은 자리로
안내하면 개인 경로는 짧아지면서 통로는 더 막힐 수 있습니다.

지금 KPI 는 전부 차량 개별 지표(주차소요, 우회거리, 재배정 횟수)입니다.
**계 수준의 양(밀도·유량·포화점)이 하나도 없습니다.** 이 문서는 그것을 어떻게
정의하고 재야 하는지를 다룹니다.

## 1. 지금 있는 배정은 사실상 "하나"다

파일은 넷입니다 — `greedy_nearest`, `hungarian_batch`, `congestion_aware`,
`zone_late_binding`. 하지만 **네 개가 모두 같은 수리 모형의 변형**입니다.

### 1.1 공통 모형

전부 아래 형태의 **가산적 개별 비용**을 최소화합니다 (`sim/control/cost.py`):

```
c(i, j) = w₁·d_drive(i,j) + w₂·n_turn(i,j) + w₃·congestion(i,j)
        + w₄·d_walk(j)   + w₅·fit(i,j)

배정:  min  Σ c(i,j)·x_ij     s.t.  Σ_j x_ij = 1,  Σ_i x_ij ≤ 1,  x ∈ {0,1}
```

차이는 **무엇을 최적화하는가**가 아니라 **언제 결정하는가 / 혼잡을 어떻게 값매기는가**
뿐입니다.

| 전략 | 무엇이 다른가 | 모형으로 보면 |
|---|---|---|
| `greedy_nearest` | 도착 순서대로 즉시 | 온라인 근시안 |
| `hungarian_batch` | 여러 대를 묶어 최적 매칭 | LAP — **단, 배치가 안 생긴다 (아래)** |
| `congestion_aware` | w₃ 를 제곱으로 | 같은 식, 벌점 함수만 볼록 |
| `zone_late_binding` | 구역만 먼저, 자리는 나중 | 같은 식, 2단계 확정 |

### 1.2 증거 ①: `hungarian_batch` 는 문자 그대로 greedy 다

D-027 에 기록돼 있습니다. 입구에 대기가 생기면 뒷차 진입이 막히므로
**같은 시간창 안에 두 대가 도착할 수가 없습니다.** 배치 크기가 2 이상이 된 적이
0 회입니다. 그래서 이 전략은 매 호출에서 greedy 와 **같은 답**을 냅니다.

### 1.3 증거 ②: 실험 결과가 구별되지 않는다

`runs/allocator-matrix/` (rush_hour, λ=0.25, 시드 10):

| 전략 | 평균 주차소요 | p95 |
|---|---|---|
| congestion_aware | 39.3 ± 3.2 | 77.4 ± 10.3 |
| greedy_nearest | 42.1 ± 4.5 | 91.5 ± 20.5 |
| hungarian_batch | 42.2 ± 4.5 | 92.0 ± 20.4 |
| zone_late_binding | 45.8 ± 6.3 | 107.9 ± 36.4 |

greedy 와 hungarian 의 차이는 0.1초, 표준편차는 4.5초입니다. **구별 불가능**합니다.
`congestion_aware` 만 2.8초 앞서는데 이것도 편차 안입니다.

> **그러므로 사용자의 직감이 맞습니다.** 파일 수가 아니라 **모형의 다양성**을 보면
> 지금 배정 시스템은 사실상 하나입니다. 그리고 넷 다 같은 모형이므로,
> 넷을 아무리 비교해도 **혼잡에 대해서는 아무것도 배우지 못합니다.**

## 2. 배정 문제를 어떻게 정형화할 수 있는가

### 2.1 정적 배정 — 선형 배정 문제 (LAP)

지금 `hungarian_batch` 가 겨냥한 것. 차량 집합 I, 빈 자리 집합 J.

```
min Σ_{i∈I} Σ_{j∈J} c(i,j)·x_ij
```

헝가리안 알고리즘으로 O(n³) 에 최적해. **전제**: 모든 차량을 동시에 안다.
현실에서는 성립하지 않습니다 — 그리고 이 주차장에서는 배치 자체가 안 생깁니다.

### 2.2 온라인 배정 — 진짜 문제의 모습

차량은 **순차적으로** 도착하고, 배정은 되돌릴 수 없습니다 (되돌리면 그게 재배정이고,
그건 D-009 의 복구 전략 영역입니다).

이건 **온라인 이분 매칭(online bipartite matching)** 입니다.

- 무가중 문제에서 greedy 의 경쟁비는 **1/2**
- Karp–Vazirani–Vazirani 의 RANKING 은 **1 − 1/e ≈ 0.632** 로 최적
- 가중 문제에서는 일반적으로 상수 경쟁비가 불가능하며, 도착 분포를 알아야 합니다

**여기서 얻는 실질적 교훈**: greedy 를 이기려면 "여러 대를 묶는 것"으로는 안 됩니다
(묶이지 않으니까). **미래에 대한 정보**를 써야 합니다.

### 2.3 확률적 동적 배정 — 해야 할 것

자리는 무작위로 비고(출차), 미래 도착도 확률적입니다. 그러면 이건 MDP 입니다.

```
상태  s_t = (주차면 점유 벡터, 통로 위 차량 분포, 시각)
행동  a_t = 도착 차량에게 줄 자리
비용  C(s,a) = c(i,j)  +  γ · E[미래 비용]
```

전부 풀 필요는 없습니다. 핵심은 **한 항**입니다:

```
c̃(i, j) = c(i, j)  +  λ_j
              ↑
        자리 j 의 기회비용 (opportunity cost)
        "지금 이 자리를 주면 나중에 누가 곤란해지는가"
```

**지금 비용 함수에는 이 항이 없습니다.** 그래서 시스템은 좋은 자리(출입구 근처)를
이른 시각에 소진하고, 나중에 도착한 차량은 멀리 보내집니다. 그 먼 이동이 통로
주행거리가 되고, 그게 혼잡입니다.

기회비용의 간단한 근사 (구현 가능한 수준):

```
λ_j = β · P(앞으로 이 자리를 더 절실히 원할 차가 온다) · (그 차가 겪을 추가 비용)
    ≈ β · (남은 시간 / 총 시간) · (d_walk(j) 의 역순위)
```

즉 **혼잡할 때는 좋은 자리를 아껴 둔다.** 항공사 좌석 재고 관리(revenue management)와
같은 구조입니다.

## 3. 혼잡을 수학적으로 정의한다

### 3.1 교통류의 기본 관계

```
q = k · v        q: 유량(대/초)   k: 밀도(대/m)   v: 평균속도(m/s)
```

혼잡이란 **k 가 늘어나 v 가 떨어지고, 결국 q 마저 떨어지는** 현상입니다.
q 를 k 에 대해 그린 것이 **기본도(fundamental diagram)** 이고, q 가 최대가 되는
지점이 **용량**입니다. 그 너머가 정체입니다.

이 주차장에서 재려면 통로 엣지 e 마다:

```
k_e(t) = (엣지 e 위의 차량 수) / (엣지 길이)
q_e    = 단위 시간당 e 를 통과한 대수
```

**지금 이 값을 아무도 세지 않습니다.** 세는 것은 어렵지 않습니다 —
`world/traffic.py` 가 이미 매 틱 모든 차량의 위치를 알고, `LaneDetection` 이
노드 통과를 이벤트로 만듭니다.

### 3.2 Little 의 법칙 — 지금 데이터로 즉시 쓸 수 있다

```
L = λ_eff · W
```

- `L`: 주차장 안에서 **주행 중인** 평균 차량 수 ← 우리가 원하는 혼잡 지표
- `λ_eff`: 실효 처리량(대/초) = 주차완료 ÷ 실행시간
- `W`: 평균 체류(주행) 시간 = `park_time_mean`

`runs/compare-baseline/` (busy, λ_offered = 0.20/s, 900초) 에 대입하면:

| | 주차완료 | λ_eff | W | **L** |
|---|---|---|---|---|
| 무안내 | 118.2 | 0.131 /s | 53.7 s | **7.05 대** |
| 안내 | 179.0 | 0.199 /s | 28.4 s | **5.65 대** |

**통로 위 차량이 평균 7.05 → 5.65 대 (−20%).**

⚠️ 다만 무안내 쪽 값은 **하한**입니다. `W` 는 *주차를 완료한* 차량만 평균 낸 값인데,
무안내에서는 900초 안에 끝내지 못한 차량이 상당수 있고 그들은 계속 돌면서도 `W` 에
들어가지 않습니다. 실제 L 은 이보다 큽니다.

### 3.3 더 중요한 것: 무안내는 이미 포화를 넘었다

같은 표를 다르게 읽으면 이 쪽이 훨씬 강한 주장입니다.

```
제공 부하(offered load) λ = 0.20/s × 900s ≈ 180 대

안내   : 179.0 대 처리 → 들어온 만큼 처리했다.  아직 용량 안쪽
무안내 : 118.2 대 처리 → 34% 를 처리하지 못했다. 이미 용량 밖
```

**같은 도착률에서 한쪽은 버티고 한쪽은 무너집니다.** 이것이 "혼잡 개선"의 가장
직접적인 형태입니다. 다만 지금은 **λ 한 점에서의 관측**일 뿐이라 곡선이 아닙니다.
포화점 λ_c 를 양쪽 다 구해야 비로소 "용량이 몇 % 늘었다"고 말할 수 있습니다
(→ 5절 실험 B).

### 3.4 혼잡의 세 층위 — 서로 다른 것을 섞지 않는다

| 층위 | 무엇인가 | 지금 지표 | 필요한 지표 |
|---|---|---|---|
| **탐색 혼잡** | 자리를 못 찾아 배회 | `detour_mean_m` (52.6 → 2.0) | ✅ 있음 |
| **밀도 혼잡** | 통로에 차가 많다 | ❌ 없음 | `L`, `k_e`, 엣지 부하 분포 |
| **상호작용 혼잡** | 서로가 서로를 막는다 | `forced_merges` (142.8 → 98.8) | 정지 비율, 교착 건수, 대기 시간 |

안내는 **탐색 혼잡을 거의 없앱니다** (−96%). 이건 확실합니다.
문제는 그 대가로 **밀도 혼잡을 키울 수 있다**는 것입니다 — 모두를 같은 곳으로 보내면.
지금 그 층위를 재는 지표가 없어서 트레이드오프가 보이지 않습니다.

`forced_merges` 는 상호작용 혼잡의 좋은 대리 지표입니다(주차면에서 통로로 나가려다
참다못해 합류한 횟수, `world/traffic.py`). 142.8 → 98.8 (−31%) 은 긍정적 신호입니다.

## 4. 배정이 혼잡을 만드는 메커니즘

### 4.1 집중–분산 트레이드오프

`cost.py` 주석에 이미 통찰이 적혀 있습니다. 정식화하면:

```
w₄ (도보거리 가중치) ↑  →  모두 A 구역으로  →  A 구역 통로 밀도 ↑  →  밀도 혼잡
w₄ ↓                    →  넓게 흩어짐      →  도보거리 ↑        →  이탈(강탈) ↑
                                                                  →  재배정 혼잡
```

**양쪽 다 혼잡을 만듭니다.** 최소가 되는 w₄ 가 어딘가 있고, 그것을 찾는 것이
실험입니다 (→ 실험 C). 지금 w₄ = 1.8 은 근거 없이 정해진 값입니다.

### 4.2 혼잡 비용은 선형이 아니다 — BPR 함수

지금 w₃ 항은 경로가 지나는 엣지들의 **점유 합**입니다 (D-013).
`congestion_aware` 가 제곱을 얹었지만(D-027), 여전히 **용량 개념이 없습니다.**

교통공학의 표준은 BPR(Bureau of Public Roads) 함수입니다:

```
t_e(x_e) = t_e⁰ · [ 1 + α·(x_e / u_e)^β ]        (통상 α=0.15, β=4)

t_e⁰ : 비어 있을 때 통과 시간
x_e  : 엣지 e 의 부하
u_e  : 엣지 e 의 용량 (대/시간창)
```

핵심은 **`u_e` (용량)** 입니다. 부하가 용량에 가까워지면 비용이 폭발합니다.
용량은 도면에서 나옵니다:

```
u_e ≈ 엣지 길이 / (차량 길이 + 안전 차간)  ÷  통과 시간
```

이렇게 하면 "이 통로는 이미 꽉 찼으니 다른 길로" 를 알고리즘이 **자동으로** 판단합니다.
지금은 값매기기(pricing)만 있고 용량이 없어서, 통로가 꽉 차도 벌점이 완만히 늘 뿐입니다.

### 4.3 ★ 사용자 최적 vs 사회적 최적 — 이 연구의 통합 틀

교통망 이론에서 두 균형을 구분합니다.

| | 정의 | 이 프로젝트에서 |
|---|---|---|
| **사용자 최적 (UE)** | 각자 자기 비용만 최소화. Wardrop 제1원리 | **무안내 베이스라인.** 운전자가 알아서 제일 가까워 보이는 자리로 |
| **사회적 최적 (SO)** | 전체 비용의 합을 최소화. Wardrop 제2원리 | **유도선 안내.** 관제가 전역을 보고 배분 |

둘의 차이가 **무정부의 대가(Price of Anarchy)** 입니다:

```
PoA = 총비용(UE) / 총비용(SO)   ≥ 1
```

> **이 시스템의 본질은 "안내판"이 아니라 "사회적 최적을 실행 가능하게 만드는 장치"입니다.**
>
> 주차장에서 SO 를 아는 것은 쉽습니다 — 관제는 모든 빈자리를 압니다.
> 어려운 것은 **그것을 운전자에게 실행시키는 것**이고, 빔 프로젝터 유도선이
> 바로 그 실행 수단입니다.

그리고 이 틀이 **강탈 연구와 혼잡 연구를 하나로 묶습니다**:

```
비협조 운전자 = SO 배분에서 이탈해 UE 로 되돌아가는 자
             = PoA 를 다시 끌어올리는 요인

복구 전략(D-009 의 6종) = 이탈이 있어도 SO 에 가깝게 되돌리는 능력
```

즉 "복구 전략 비교"는 **어느 전략이 PoA 를 가장 낮게 유지하는가**로 다시 쓸 수 있고,
그러면 개별 지표(재배정 횟수)가 아니라 **계 전체의 효율**로 평가하게 됩니다.
발표에서 훨씬 강한 논지입니다.

## 5. 새로 만들 배정 모형 — "진짜 다른" 것들

지금 넷은 같은 모형이므로, 아래는 **모형 자체가 다른** 후보들입니다.

| 이름 | 모형 | 무엇을 새로 답하나 | 난이도 |
|---|---|---|---|
| `walk_only` | w₄ 만, 나머지 0 | **극단 대조군.** 집중 혼잡의 상한 | 낮음 |
| `spread_only` | 통로 부하 최소화만 | **반대쪽 극단.** 분산의 상한 | 낮음 |
| `flow_bpr` | BPR 볼록 혼잡비용 + 엣지 용량 | 혼잡이 비선형일 때 배정이 달라지는가 | 중간 |
| `opportunity_cost` | c + λ_j (자리의 미래 가치) | 좋은 자리 조기 소진을 막으면 나아지는가 | 중간 |
| `system_optimum` | 전체 비용 합 최소화 (오프라인, 사후) | **PoA 의 분모.** 이론적 하한 | 중간 |

`walk_only` 와 `spread_only` 를 먼저 만들 것을 권합니다. **둘 다 나쁜 전략인 것이
확실한데도** 가치가 있습니다 — 나머지 전략들이 그 사이 어디에 있는지 좌표를 주기
때문입니다. 지금은 넷이 몰려 있어서 좌표가 없습니다.

`system_optimum` 은 실시간으로는 불가능합니다(미래를 알아야 하므로). 실행이 끝난 뒤
전체 도착 목록을 알고 계산하는 **사후 최적**으로 두면 PoA 의 분모가 됩니다.

## 6. 실험 설계 — Q2 에 답하는 순서

### 실험 A — Little 의 법칙 (지금 데이터로 즉시)

계산만 하면 됩니다. `sim/experiments/report.py` 에 `L = parked/duration × park_time_mean`
한 줄을 더하면 모든 기존 실행에 소급 적용됩니다. **비용 0.**

### 실험 B — 포화 곡선 ★ 가장 중요

```
λ ∈ {0.10, 0.15, 0.20, 0.25, 0.30, 0.35, 0.40, 0.45}
조건: 무안내 / greedy_nearest
시드 30, 각 1800초 (정상상태 도달까지 여유)
```

출력:
- **λ vs 처리량** — 두 곡선이 꺾이는 지점 λ_c 를 비교. "용량이 X% 늘었다"
- λ vs 평균/p95 주차소요 — 무릎(knee) 위치
- λ vs L — 밀도가 언제 폭발하는가

> 이 그래프 한 장이 **공모전 발표의 핵심 슬라이드**가 되어야 합니다.
> "같은 도착률에서 한쪽은 무너지고 한쪽은 버틴다"를 눈으로 보여줍니다.

### 실험 C — 집중–분산 스윕

```
w₄ (도보거리 가중치) ∈ {0, 0.6, 1.2, 1.8, 2.4, 3.0, 4.0}
시나리오: busy, 시드 30
```

출력: w₄ vs (평균 도보거리, 통로 밀도 L, 이탈률) 3자 곡선.
**최적 w₄ 를 근거를 갖고 정할 수 있게 됩니다.** 지금 1.8 은 임의값입니다.

### 실험 D — 무정부의 대가

```
총비용 = Σ (주행거리 + κ·도보거리)  ← κ 는 실험 C 에서 정한 환산율

PoA_무안내 = 총비용(무안내) / 총비용(사후 최적)
PoA_안내   = 총비용(greedy) / 총비용(사후 최적)
PoA_안내(비협조 35%) = ...
```

출력: "안내는 PoA 를 A → B 로 낮춘다. 비협조 35% 는 그중 C 만큼을 되돌린다."

### 실험 E — 비협조 비율 스윕

```
noncompliant_share ∈ {0, 0.15, 0.35, 0.60, 1.00}
```

출력: **안내의 이득이 언제 사라지는가.** 비협조 100% 면 무안내와 같아져야 정상이고,
그렇지 않다면 모델에 문제가 있다는 뜻입니다 (좋은 정합성 검사입니다).

## 7. ⚠️ 측정 타당성 위협 — 실험 B 전에 반드시 고칠 것

`sim/world/simulation.py:418`:

```python
guided = sum(1 for v in self.vehicles if v.parked_t is None)
if self._backlog == 0 or guided >= cfg.max_guided:
    return          # 입구에서 차량 생성을 막는다
```

`max_guided` 는 **주차하지 않은 모든 차량**을 세며, **무안내 모드에도 똑같이 적용**됩니다
(`baseline.yaml` 도 `max_guided: 20`).

문제는 이 값의 근거입니다. 20 은 **유도선 색 구분의 한계**에서 나온 숫자입니다(D-006).
무안내 모드에는 유도선이 없으므로 이 제약은 물리적 근거가 없습니다.

**그런데 이 제약이 처리량 비교를 지배하고 있을 수 있습니다:**

```
무안내 → 차가 오래 돈다 → 미주차 차량이 20 에 닿는다 → 입구가 막힌다
      → 도착이 억제된다 → 처리량이 떨어진다
```

이렇게 되면 "무안내가 118 대밖에 처리 못 했다"는 결과가 **물리적 혼잡 때문인지
색 팔레트 한계 때문인지 구분되지 않습니다.**

### 고칠 방법

두 상한을 **분리**해야 합니다:

| 이름 | 의미 | 적용 | 값의 근거 |
|---|---|---|---|
| `max_guided` | 동시에 **안내 가능한** 대수 | 안내 모드만 | 색 팔레트 (D-006) |
| `max_circulating` | 주차장이 물리적으로 담을 수 있는 주행 차량 수 | **양쪽 모두** | 통로 총 길이 ÷ (차량 길이 + 차간) |

`max_circulating` 은 도면에서 계산해야 합니다(`aisle_width` 손잡이처럼, D-019).
그래야 "포화"가 실제 도로 용량을 뜻하게 됩니다.

> 이걸 고치기 전에 실험 B 를 돌리면, 나오는 포화점 λ_c 는 주차장의 용량이 아니라
> 상수 20 을 재는 것이 됩니다.

## 8. 지금 말할 수 있는 것과 없는 것

### 말할 수 있다 (근거 있음)

- **탐색 혼잡은 거의 사라진다.** 우회거리 52.6m → 2.0m (−96%), p95 241m → 8.4m
- **개별 소요시간이 절반이 된다.** 53.7초 → 28.4초 (−47%), p95 −59%
- **상호작용 혼잡이 준다.** 강제 합류 142.8 → 98.8 (−31%)
- **같은 도착률에서 처리량이 51% 높다** (118.2 → 179.0대)
- 세 지표가 **같은 방향**을 가리킨다 — 예비 증거로는 충분히 강하다

### 아직 말할 수 없다 (측정이 없음)

- "통로 밀도가 줄었다" — `k_e` 를 세지 않는다
- "용량이 X% 늘었다" — 포화 곡선이 없다. 점 하나뿐
- "혼잡을 개선한다" — 위 7절의 혼입 때문에 지금 처리량 차이를 그대로 인용하면 위험하다
- "이 배정 전략이 저것보다 덜 혼잡하다" — 넷이 같은 모형이라 비교가 성립하지 않는다

### 절대 하면 안 되는 주장

> "우리 시스템은 주차장 혼잡을 31% 줄입니다"

`forced_merges` 는 상호작용 혼잡의 **대리 지표**이지 혼잡 자체가 아닙니다.
숫자 하나를 뽑아 "혼잡"이라고 이름 붙이면 질문받을 때 방어할 수 없습니다.
층위를 나눠서(3.4절) 각각 무엇을 쟀는지 말하는 편이 훨씬 강합니다.

## 10. 정직하게 남겨둘 한계

- **도착 과정이 포아송**입니다(베르누이 근사). 실제 주차장은 신호 주기·행사 종료 등으로
  뭉쳐서 도착합니다. 뭉친 도착에서는 혼잡이 훨씬 나쁩니다
- **운전자는 유도선을 항상 봅니다.** 실제로는 못 보거나 헷갈릴 수 있고, 그 확률이
  안내의 이득을 직접 깎습니다
- **주차면·통로 치수가 현실 규격보다 큽니다** (D-018/D-019). 통로 14m 는 왕복 2차선
  도로 폭이라 교행이 실제보다 쉽습니다. 현실 치수(7m)에서는 혼잡이 더 심할 것입니다
- **주차장 밖은 모델 밖입니다.** 입구 앞 도로에 생기는 대기열(진입 대기)이 실제로는
  가장 눈에 띄는 혼잡인데, 여기서는 `_backlog` 숫자로만 존재합니다
- **한 도면에서만 쟀습니다.** 규모·형상이 다른 주차장에서 같은 결론이 나오는지는
  모릅니다. `GridSpec` 으로 크기를 바꿀 수 있으니 검증은 가능합니다
